# OMS 단독 완결: 기능 공백 backlog

검토일: 2026-11-10. OMS 조사 기준 `55af18c`, 게시 기준 `0bc92b3`. 상태: 제안 / 문서 전용.
[기존 계획](CONTROL-PLANE-EVOLUTION.md), [UX/NF 설계](CONTROL-PLANE-UX-AND-FEATURES.md),
[기존 비교와 정정](CONTROL-PLANE-REFERENCES.md), [기능 확장](FUNCTIONAL-EXPANSION-20261109.md)을
대체하지 않는다. 그 문서들이 패널과 control plane을 다뤘다면, 이 문서는
**companion 도구 없이 OMS만으로 일이 닫히려면 무엇이 비는가**를 여덟 영역에서 나열한다.
여기 적힌 항목은 수락된 계획이 아니다. 새 public CLI·schema·기본값·환경변수는 항목마다 별도 검토 대상이고,
수락 조건 체크박스는 이 문서로 바뀌지 않는다.

## 요약

oh-my-setting(OMS, VERSION 0.7.0, 조사 기준 `55af18c`)이 companion 없이 완결된 하네스가 되는 데 필요한 것은 새 엔진이 아니라 **이미 쌓고 있는 기록을 서로 잇고, 라이브 세션에 닿게 하고, 실행을 지키는 확장 137개**이며 그중 **52개가 P1**이다. 여덟 영역을 조사한 노트의 공통 결론은 같다. OMS는 쓰는 쪽(공유 메모, Work Journal, 수락 기준 ID, 내용 없는 hook 텔레메트리, run capsule, review artifact)을 이미 갖췄고, 비어 있는 곳은 그 기록이 메인 세션·계획·비교·리뷰 수명주기로 돌아오는 읽기 경로와 연결 고리다. 예외가 안전 영역이다. 도구 호출을 사전에 거부하는 hook이 좁은 조건의 하나뿐이고, Claude write 워커는 OS 샌드박스 없이 운영자 권한을 상속하며, 시크릿 읽기를 막는 장치가 없다. 이 부분은 노트가 "companion 없이 서야 하는 핵심 보호"로 분류했다. 나머지 P1은 요구사항 ID에서 task와 증거로 가는 추적, 리뷰 finding 수명주기, 메모의 대체·철회, metric 계약과 seed 집계, 날짜별 사용량과 통합 검색, Python·shell 밖 언어의 구조 추출, 설치 dry-run이다. 반대로 임베딩 검색, LSP, OS 샌드박스 런타임, managed PR 리뷰어, tracking 서버, MCP 게이트웨이는 선택형 companion으로 남기고, 자동 merge·approve, 백그라운드 LLM 통합, egress 프록시, 토큰에서 quota를 추론하는 계산은 넣지 않는다. 영역 사이에 같은 부품을 요구하는 묶음 14개를 한 번에 만들면 PR 수가 줄고, 착수는 "probe와 소유자 결정 → 이미 있는 데이터를 쓰이게 하는 S 확장 15개 → 안전 바닥 → 추적 뼈대 → 관측·컨텍스트·설치" 순서가 맞다. 다만 이 보고서의 OMS 서술은 전부 문서·코드·`--help`의 정적 읽기이고 외부 도구는 하나도 실행하지 않았으며, 노트 네 개는 검색 한도 소진으로 일부 1차 자료를 열지 못했다.

## 이 backlog를 읽는 기준

**확인 수준**은 노트의 표기를 그대로 옮겼다. `문서`는 조사자가 직접 연 공식 문서·공식 README·논문·패키지 레지스트리, `보조`는 제3자 글·미러·집계 사이트, `미확인`은 이번에 1차 자료를 열지 못한 것(ML 노트에서는 모델 사전지식 기준)이다. 각 영역 표 앞의 "출처" 줄이 프로젝트별 수준과 주소를 한 번씩 밝히고, 표 안에서는 **문서 수준이 아닌 근거에만 (보조)·(미확인)을 붙였다**. OMS 쪽 서술의 근거는 `55af18c` 체크아웃의 파일과 도움말이며, 실행으로 검증한 것은 없다. 외부 프로젝트의 star 수, 자가 보고 절감률, 벤더 벤치마크 수치는 근거에서 뺐다.

**ID**는 노트의 영역별 번호를 보존하고 영역 접두사만 붙였다: `MEM`(메모리·지식), `SPEC`(spec·계획), `SAFE`(안전·sandbox), `OBS`(사용량·관측·알림), `CODE`(코드 인텔리전스·컨텍스트), `REV`(리뷰·CI·PR 자동화), `DIST`(스킬·설치·설정 배포), `ML`(ML/HPC 연구). 노트가 한 번호를 둘로 나눈 곳(`SPEC-G4a/G4b`, `SAFE-G5a/b/c`)은 그대로 두었고, spec 노트에는 G15가 없다(결번).

**크기와 우선순위**는 조사자의 추정이지 관리자의 실측이 아니다. 노트마다 척도 표현이 조금 다르지만 뜻은 같다. S는 기존 스크립트 한두 개와 기존 테스트의 확장(대략 PR 1개), M은 새 하위 명령이나 모듈과 fixture(PR 2~3개), L은 설치 계약·여러 구성요소·플랫폼별 구현에 걸치는 일이다. P1은 companion 없이 서는 데 필요한 것, P2는 있으면 companion이 필요 없어지는 것, P3는 확신이 낮거나 여유 있을 때 할 것이다. AGENTS.md의 "canonical 테스트를 먼저 확장" 규칙 때문에 실제 비용은 대상 스크립트의 테스트 구조에 좌우된다.

**제약**은 모든 "만드는 법"의 전제다. 라이브 main은 하나, 상태 정본은 `.oms/` 파일(JSONL과 파일 잠금), 상주 데몬·두 번째 권위 DB·새 필수 의존성·기본 네트워크 노출·유료 API 자동 전환·자동 kill·자동 merge는 없고, 관측 결과는 승인이나 검증의 근거가 아니다. "만드는 법"은 노트의 설계 추론이며 OMS 코드로 검증한 구현 계획이 아니다.

### spec·계획 17개: 기준 ID 기능은 있는데 계약이 그것을 채우지 않는다

OMS runtime은 `[id:…]` 기준 ID와 기준별 evidence 상태를 이미 지원하지만, 스펙 템플릿·`intent draft` 스켈레톤·인터뷰 스킬 어디도 ID를 요구하지 않고 plan 제안 스키마에는 기준 연결 필드가 없다. 그래서 기능이 있어도 데이터가 채워지지 않는다. 두 번째 빈칸은 확정된 `PROJECT.md`를 바꾸는 정식 경로다. `intent adopt`는 기존 파일이 있으면 거부하고 손 편집은 plan을 바이트 드리프트로 묶는다.

### 안전·sandbox 13개: 사후 탐지는 두텁고 사전 거부와 읽기 차단이 얇다

OMS의 쓰기 경계(`patch-admit` → `patch-land` → `land`)는 조사 범위에서 가장 엄격한 축에 든다. 얇은 곳은 그 앞단이다. 일반 세션의 `rm -rf`나 `git reset --hard`를 막는 가드가 없고, Codex 플러그인 hook에는 PreToolUse가 없으며, Claude write 워커는 운영자의 native 권한을 그대로 상속한다. 노트는 이 영역의 P1을 "companion 없이 서야 하는 핵심 보호"로 정의했고, 동시에 hook 가드는 `sh -c`나 하위 프로세스를 원리적으로 막지 못하므로 "사고 방지"로만 문서화해야 한다고 못 박았다.

### 사용량·관측·알림 17개: 지표는 쌓이는데 날짜별 보고와 연결점이 없다

OMS의 원칙(보고값만, 미보고는 0이 아님, 본문은 알림에 싣지 않음)은 조사한 외부 도구 대부분보다 보수적이고, 노트는 그 원칙을 바꾸지 않는 선에서 공백을 정의했다. 비어 있는 것은 날짜·모델·역할별 집계, 5시간 창, 임의 알림 명령으로 넘기는 연결점, `.oms` 기록 통합 검색이다. `rate_limits`가 Pro/Max 가입자에게만, 세션의 첫 API 응답 뒤에만 나온다는 한계는 어떤 구현으로도 사라지지 않는다.

### 리뷰·CI·PR 17개: finding이 자유 서술이라 수명주기가 없다

OMS의 독립 리뷰는 "같은 계열은 한 의견"이라는 원칙과 기계적 `--verify` backstop으로 조사 대상 managed 리뷰어보다 엄격하다. 빈 곳은 finding 자체다. 안정 ID와 상태가 없고, 후속 gate에는 직전 findings가 3000 bytes로 잘려 전달되며, 인용한 file:line이 실제 diff hunk 안에 있는지 확인하지 않는다. CP-10이 "새 finding authority store는 만들지 않는다"고 못 박았으므로 해법은 기존 artifact-index row와 projection 안에 있어야 한다. GitHub 쪽은 읽기(branch protection, PR comment, merge 뒤 확인)가 통째로 없다.

### ML/HPC 연구 23개: run·데이터·metric·주장 사이의 기계적 연결이 없다

OMS는 run을 기록하고(ledger, capsule), 데이터를 지문으로 고정하고(manifest), 실험을 사전 등록한다(ExperimentContract). 셋이 서로를 모른다는 것이 이 영역의 핵심 공백이다. ledger·capsule·experiment 코드 어디에도 manifest 참조가 없어 "이 숫자는 어느 split 버전에서 나왔나"를 기계로 답할 수 없다. 이 연결이 없을 때의 실패는 문헌에 있다. AI Scientist-v2 저자들은 워크숍 통과 논문에서 train/test 데이터 겹침 약 57%를 직접 보고했고([문서](https://arxiv.org/pdf/2504.08066)), RE-Bench에서는 에이전트가 학습을 건너뛰고 출력을 복사해 검사를 속인 사례가 관측됐다([문서](https://metr.org/blog/2024-11-22-evaluating-r-d-capabilities-of-llms)). 노트의 P1 정의는 "plan → run → track → compare → report 루프를 companion 없이 닫는 것"이며, 탐색 알고리즘과 tracking 서버는 끝까지 밖에 둔다.

## companion으로 남길 것은 서버·모델·계정이 전제인 기능이다

0단계의 **probe**는 일곱 가지다. 설치된 Codex의 pre-tool hook 계약(SAFE-G3), headless `claude -p` 워커에 호출별 `--settings`의 sandbox 키가 의도대로 적용되는지(SAFE-G5a), `isolated` 백엔드가 위임·검증 경로에 실제로 연결돼 있지 않은지(SAFE-G5b, ML-G17), `resume-hook.sh`가 `source=compact`를 구분하는지와 현재 주입 길이(MEM-G1, CODE-G6), F5의 cumulative/delta 정리와 #16 R2 parser 수정의 현재 상태(OBS-G1, OBS-G5), 현재 Codex가 `~/.codex/skills`를 계속 읽는지(DIST 전반), Antigravity의 `mcp(server/*)` 규칙이 headless CLI에서 유효한지(SAFE-G10)다.

## 확인하지 못한 것

**조사 방법의 한계.** 외부 도구는 하나도 설치하거나 실행하지 않았다. 모든 서술은 문서가 말하는 동작이지 검증한 동작이 아니다. OMS 쪽도 문서·코드·`--help`의 정적 읽기이며, "없음" 판정 다수는 `scripts/`와 `docs/`의 grep에 근거한다(`tests/`, `plugins/`, `custom-skills/` 안의 보조 구현은 전수 확인하지 않았다). 안전, 리뷰·CI, 배포, ML/HPC 노트는 조사 도중 웹 검색 한도가 소진돼 일부 대상의 1차 자료를 열지 못했다. Codex 공식 문서는 `developers.openai.com`에서 `learn.chatgpt.com`으로 리다이렉트되고 일부 대상 페이지가 열리지 않거나 잘렸다. GitHub 릴리스 페이지가 연도를 생략한 날짜는 2026년으로 추정한 것이다.

## 결론

이 조사가 바꾸는 것은 "단독 완결"의 정의다. 137개 가운데 새 최상위 verb를 요구하는 것은 여섯 개(`deps`, `claims`, `figure`, `cite`, `slurm-lint`, `structure-digest`)뿐이고 나머지는 기존 verb의 플래그, 읽기 뷰, 행 필드다. OMS에 부족한 것은 기능의 수가 아니라 닫힌 루프의 수다. 메모가 세션으로 돌아오는 루프, 기준이 task를 거쳐 증거로 돌아오는 루프, finding이 수정을 거쳐 해소로 돌아오는 루프, 숫자가 run과 데이터 지문으로 돌아오는 루프가 각각 한두 개의 연결 고리를 빼고는 이미 서 있다. 그래서 backlog의 진척은 "몇 개를 넣었나"보다 "어느 루프가 닫혔나"로 재는 편이 맞고, 3단계의 ID 뼈대가 그 척도의 중심이다. 다만 `AGENTS.md`의 "verb 하나에 철자 하나"와 "테스트를 더하는 커밋은 대체할 테스트를 찾는다"는 규칙을 생각하면, 여섯 개의 새 verb는 기존 verb의 하위 명령으로 접을 수 있는지 먼저 따지고, `doctor`에 붙는 읽기 전용 플래그들(`--security`, `--mcp`, `--extensions`, `--budget`, `--team`)은 하나의 finding ID 형식으로 묶어야 테스트와 표면이 함께 불어나지 않는다. 이 두 가지는 노트가 다루지 않은, 통합 단계에서 생기는 비용이다.

외부 생태계의 움직임은 OMS의 제약이 약점이 아님을 보여 준다. Agent OS는 v3에서 구현·오케스트레이션 단계를 걷어 냈고, BMAD는 core를 줄였으며, managed 리뷰어들은 대부분 PR을 막지 않는 advisory로 남았고, provider들은 plan mode, auto memory, 샌드박스, 코드 리뷰를 직접 흡수하고 있다. 이 흐름에서 OMS가 오래 가질 수 있는 가치는 native 기능의 재구현이 아니라 **세 provider에 걸친 계약과 증거**다. backlog에서 `doctor` 계열과 영수증 계열(읽고, 대조하고, 낡았음을 알리는 항목)이 가장 오래 살아남을 투자이고, 반대로 native가 이미 잘하는 것을 따라가는 항목(추정 비용 열, burn rate 외삽, 랭킹 검색)은 실제 사용 데이터가 필요를 증명한 뒤에 착수해도 늦지 않다.
